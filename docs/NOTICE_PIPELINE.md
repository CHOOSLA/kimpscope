# 실제 공지 수신 단계

기존 documents.json의 개별 원문을 확인하지 못한 요약문은 verified=true가 없어 RAG에서 제외된다. 파일은 감사용으로 보존한다. 기존 벡터 청크도 해당 코인의 다음 질의 시 현재 선택 문서 목록에 맞춰 제거된다.

서버 환경변수 UPBIT_ACCESS_KEY, UPBIT_SECRET_KEY를 설정하고 재시작하면 공식 Private WebSocket의 announcement를 include_body=true로 구독한다. 키 값은 로그/상태 API에 노출하지 않는다. 자동 실행은 키가 모두 있을 때만 한다.

- /api/notices/status: 연결 상태, 마지막 이벤트 수신 시각, 이력 불완전 여부
- 공지 UUID로 중복 제거. timestamp가 더 큰 수정만 수락한다.
- body가 null인 최신 수정은 이전 본문을 제공하지 않는다. 후속 본문 수집은 아직 미구현이다.
- 제목/본문에 심볼이 명시된 코인만 연결한다. 한국어 이름만 있는 공지와 공통 공지는 자동 매핑하지 않는다.
- 수신 원문은 SQLite에 저장한다. 문서 선택 캐시는 원문/개정 변경 시 해시가 달라져 재사용되지 않는다.
- 임베딩은 질문 시 수행한다. 즉시 백그라운드 색인은 아직 구현하지 않았다.
- 질문별 문서 정리와 검색을 한 잠금으로 보호한다. 모델 호출까지 직렬화되는 성능 제한이 있다.
- 재연결은 최대 60초 백오프. 과거 공지 조회/연결 중 누락 복구는 미구현이다. 연결 직후 새 공지가 없으면 수신이 없는 것이 정상이다.

공식 명세: https://docs.upbit.com/kr/reference/websocket-announcement

Render free의 로컬 디스크는 영속 저장소가 아니다. 현재 설정에서는 재시작/재배포 시 원문·색인이 손실될 수 있다. 상시 공지 수신과 과거 이력 보존을 운영하려면 지속 실행·영구 디스크 또는 외부 저장소를 먼저 정해야 한다. 이 단계는 로컬 구현이며 배포 완료로 간주하지 않는다.

## 빗썸 공개 API 대체 경로

API 키 없이 `https://api.bithumb.com/v1/notices?count=20` 조회. 기본 300초, 최소 60초 간격으로 실행한다. 목록 API는 최신 20개까지이므로 전체 과거 이력이나 누락 없는 수집을 보장하지 않는다.

개별 `https://feed.bithumb.com/notice/{숫자}` 주소만 본문 수집 대상으로 허용한다. 상세 페이지 요청은 1.1초 간격이며 리다이렉트를 따라가지 않는다. main 본문을 찾지 못하거나 요청이 실패하면 제목/URL만 저장하고 RAG 근거에서 제외한다. 다음 주기에 재시도한다. 원문 이용 조건 확인은 별도로 남아 있다.

수정 시각을 기준으로 중복·역순 업데이트를 방지하며 동일 수정 시각의 본문 변경은 감지하지 못한다. 목록 밖으로 밀려난 과거 공지의 수정도 감지할 수 없다. 질문 때 실제 저장 원문을 코인 심볼로 연결하고 재색인한다. 거래소는 Bithumb으로 표시하며 업비트 상태를 추론하지 않도록 생성 지침을 적용한다.

`BITHUMB_NOTICES_ENABLED=false`로 자동 수집을 끌 수 있다. `/api/notices/status`에서 upbit/bithumb 상태를 각각 확인한다.

2026-10-23 로컬 실요청: 인증 없이 2건 목록/본문 수집 확인. 전체 공지 이력이나 운영 환경 수신을 검증한 것은 아니다.

공식 명세: https://apidocs.bithumb.com/reference/공지사항-조회

실제 RAG 검증: ONT 질의가 개별 빗썸 공지 1655357을 인용했고, 공지에 기록된 10월 22일 오후 7시 중지 시점 및 Ontology 네트워크를 설명했다. 현재 상태는 확인 불가로 답했다. 테스트 20개 통과. 원문 본문 수집·코인별 문서 API·임베딩 검색·생성까지 로컬에서 확인했다. 수집기가 지속 실행되는 운영 배포와 장기 수정 감지는 별도 검증이 필요하다.

수집 상태 보강: 마지막 성공 시각과 최근 목록의 가장 오래된 게시 시각을 SQLite에 보존한다. 기존 기록과 새 목록에 겹치는 URL이 전혀 없으면 possible_gap=true로 표시한다. 이는 누락 확정이나 전체 이력 복구를 의미하지 않으며, 이 DB 자체도 현재 Render 로컬 디스크에서는 영속적이지 않다. 회귀 포함 21개 테스트 통과.
